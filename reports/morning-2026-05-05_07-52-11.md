### Branch 2 — `fix/alpaca-bar-adapter-pagination` (merged `--no-ff` into `dev`)

**Severity:** correctness defect in historical-bar fetches. Affected any caller asking for more rows than fit in one Alpaca page (1m bars over a multi-week window is the realistic case).

**Root cause.** `broker/alpaca/api/bar_api.py::AlpacaBarAdapter.get_bars` issued a single request with `limit=10000` and ignored `next_page_token` from the response. Alpaca's `/v2/stocks/bars` endpoint paginates beyond the limit; ignoring the token silently truncates the result set. A 1m series across ~16+ trading days exceeds the 10k cap, so a backtest-style consumer would have used short data without any signal that data was missing.

**Fix.** Wrapped the single GET in a loop that follows `next_page_token` on each iteration, capped at `_MAX_PAGES=200` to short-circuit any server-side token loop. Concatenates rows across pages.

**Tests added.** Two regression tests in `tests/broker/alpaca/test_bar_adapter.py`:
- `test_get_bars_follows_next_page_token` — drives a 2-page response (page 1 with `next_page_token="page-2-token"`, page 2 with `None`) through `httpx.MockTransport`, asserts the adapter sees both tokens and returns 3 concatenated bars.
- `test_get_bars_does_not_loop_when_no_next_page_token` — single-page response must short-circuit after one HTTP call.

**Verification.** `uv run --no-sync pytest tests/broker/alpaca/test_bar_adapter.py` — all 4 tests pass.

**Branch / merge status.** Committed `01769023`, merged `--no-ff` into `dev` as merge commit, branch deleted.

### Branch 3 — `fix/alpaca-validate-combo-per-leg` (merged `--no-ff` into `dev`)

**Severity:** correctness + UX. Combo orders (bracket / OCO / OTO / OTOCO) bypassed per-leg validation despite a docstring promising it.

**Root cause.** `AlpacaOrderTranslator.validate_combo`'s docstring claims:

> Reuses validate() for each leg's per-leg constraints (venue, order type, etc.) then layers combo-specific shape checks

…but the body never calls `self.validate(...)`. Per-leg invariants (venue ∈ `_SUPPORTED_VENUES`, order_type ∈ `_SUPPORTED_TYPES`, time_in_force ∈ `_SUPPORTED_TIF`, session ∈ `_SUPPORTED_SESSIONS`, `quantity_unit ≠ LOTS`, extended-hours type/TIF gating) were not checked at validate-time. Some defects still tripped at serialization with the wrong capability code (e.g. an unsupported `order_type` would surface a `*_price` failure from `to_native_combo` instead of the more accurate `order_type` capability code).

**Fix.** Added a small module-level shim `_ComboLegOrder` (slotted, hashable-friendly) that exposes a leg's per-leg fields plus the combo-level TIF / session / extended-hours flag in the shape `validate()` reads. `validate_combo` now iterates `(leg, instrument)` pairs and calls `self.validate(synthetic, instrument, account_ctx)` per leg before the existing combo-shape checks. Existing combo-shape checks (leg count, take_profit/stop_loss type discipline, cross-symbol invariant) are preserved.

**Tests added.** Two regression tests in `tests/broker/alpaca/test_order_translator_combo.py`:
- `test_validate_combo_rejects_unsupported_leg_venue` — leg routed to XLON (Alpaca doesn't trade) is now rejected at validate-time with `capability_name == "venue"`.
- `test_validate_combo_rejects_lots_quantity_unit_in_a_leg` — leg with `QuantityUnit.LOTS` now rejected at validate-time with `capability_name == "quantity_unit"`.

**Verification.** All 14 combo tests + 27 existing single-order translator tests pass after the change (46 total, all green).

**Branch / merge status.** Committed `f07cd8bb`, merged `--no-ff` into `dev` as merge commit, branch deleted.

### Branch 4 — `fix/auth-token-negative-cache-blocks-recovery` (merged `--no-ff` into `dev`)

**Severity:** correctness. A revoked → restored credential was silently blocked from authenticating for the rest of the session window (up to 24 hours).

**Root cause.** `database/auth_db.py::get_auth_token_broker` cached negative results `(None, None)` into `auth_cache`, which has a TTL tied to the next session expiry — anywhere from 5 minutes to 24 hours. After a token was revoked (or briefly missing) and then restored, the next lookup short-circuited on the poisoned `(None, None)` entry instead of re-querying the DB. Operators recovering a credential mid-day had no way to know the cache was the blocker; the symptom was "I restored the key, why is it still rejecting orders?". The intent of the cache write — dampening DB load from background pollers chasing revoked sessions — is legitimate, but the long TTL is wrong for that purpose.

**Fix.** Split the negative-result path into a separate `revoked_auth_cache = TTLCache(ttl=300)` (5 minutes). The main `auth_cache` no longer stores `(None, None)` tuples. Negative lookups still short-circuit (preserving the load-shedding intent) but the blackout is bounded to 5 minutes. The cache is keyed on a SHA256 of the API key, mirroring the existing positive-result cache, so the plaintext key never lands in an in-memory dict.

**Tests added.** Three regression tests in `tests/database/test_auth_db_negative_cache.py` (newly created package) using `monkeypatch` to fake `verify_api_key` and `Auth.query` so the cache logic runs without a DB:
- `test_revoked_token_does_not_poison_long_lived_auth_cache` — revoked lookup MUST leave `auth_cache` empty.
- `test_recovery_returns_real_token_after_negative_cache_expires` — revoked → cleared negative cache → restored token is now visible.
- `test_revoked_negative_cache_short_circuits_within_ttl` — within the 5-minute TTL, repeat revoked lookups make exactly 1 DB call.

**Verification.** All 3 new tests pass. Re-ran the existing `tests/contracts/test_session_tz_fail_closed.py` (which loads the same module) — all 5 pre-existing tests still pass.

**Branch / merge status.** Committed `7098baf0`, merged `--no-ff` into `dev` as merge commit, branch deleted.

## Recommendations for the human reviewer

1. **Address Open Issue #1 (Alpaca legacy mapping module).** This is the single biggest friction point a Phase-2 sweep can identify without making a product decision: 4 of the 5 read-only legacy v1 endpoints are dead for Alpaca. The fix is a faithful translation of Alpaca's order/position field shapes into the existing v1-frozen schema, not an architectural change.
2. **Decide on Open Issue #4 (broker_cache parity with auth_cache).** Branch 4 fixed the high-impact sibling; the broker_cache half is a 10-line follow-up but requires a deliberate review because the cache is held to a 50-minute TTL (long enough that revocation lag is real, short enough that recovery is bounded).
3. **Audit other broker plugins for the bar-pagination pattern.** The `next_page_token` / `cursor` pattern is common to multiple US/EU brokers; if anyone else added a "limit=10000 and call it a day" loop, the same silent-truncation bug exists. The Branch 2 test scaffolding (httpx MockTransport with a 2-page handler) is reusable.
4. **Audit other auth-related caches for negative-result poisoning.** Branch 4 surfaced one. The same anti-pattern (caching `None` with a long TTL to dampen background-poller load) likely lives elsewhere — `verified_api_key_cache`, `feed_token_cache`, etc. should be inspected for symmetric defects. Mechanical pattern to grep: `_cache[*] = (None, …)` or `_cache[*] = None` with a long-TTL cache definition.
5. **Promote `tests/database/__init__.py` from this session.** It's a new top-level test package (created today) and the focused unit-test pattern in it (monkeypatch `Auth.query` + `verify_api_key` to test cache behavior without a real DB) is the lightest viable test setup for the remaining `auth_db.py` cache surfaces. Re-use it for Issue #4 if you act on Recommendation 2.
6. **Replace the morning-debug sandbox with this run's environment.** The earlier `reports/morning-2026-05-05.md` documents three sandbox failures (firewalled network, Linux interpreter against Windows venv, bash-vs-Edit filesystem divergence). This session ran in a clean local environment and the entire prompt completed end-to-end. If the morning task is re-scheduled to run automatically, reproducing this environment (Windows host, native `.venv`, real network) is a hard prerequisite.
