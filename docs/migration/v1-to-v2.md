# `/api/v1` → `/api/v2` migration guide

This document is the per-endpoint mapping reference for the
operator-driven v1→v2 migration that v5 Phase 8 announces.

**Status**: v1 is **deprecated** as of v5 Phase 8 (D-1). Every
`/api/v1/*` response now carries `Deprecation: true` + `Sunset:
<date>`. The sunset date defaults to *deployment-time + 180 days*;
operators override it via the env var `OPENALGO_V1_SUNSET_DATE`
(ISO 8601 date).

v1 remains live for the entire sunset window. Removal is **outside
v5 scope** and lands in v6.

## Per-broker readiness

Per-broker v2 readiness is tracked in
`docs/refactor/v5_india_v2_readiness_matrix.md`. As each India
broker completes Phase 8-bis (translator + parity harness),
operators can flip `API_V2_<BROKER>=1` for that broker.

## Response shape compatibility

* v2 response shapes are a **superset** of v1: every v1 field
  appears in the v2 response; v2 may add fields a v1 client did not
  see. Existing v1 clients that read by field name continue to
  work.
* v2 routes are RESTful: GET for reads, POST for writes; v1 was
  POST-everywhere. v2 also accepts the v1 POST shape on the
  matching v2 endpoint as a transition convenience for some routes
  (Phase 8-bis decides per route whether to keep the convenience).

## Deprecation headers

Every `/api/v1/*` response carries:

* `Deprecation: true` — RFC 8594.
* `Sunset: <ISO date>` — operator-controlled via
  `OPENALGO_V1_SUNSET_DATE`.
* `Link: <https://docs.openalgo.in/migration/v1-to-v2>; rel="deprecation"`.

Clients should log requests that observe these headers and plan a
migration before the sunset date.

## Out of scope (v5)

* Per-broker translator implementation (Phase 8-bis).
* Per-broker v2 parity harnesses (Phase 8-bis).
* The actual sunset date enforcement (v6 — return 410 after
  sunset).
* Removal of v1 routes (v6 — after sunset).
