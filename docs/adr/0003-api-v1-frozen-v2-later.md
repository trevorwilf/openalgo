# ADR 0003: `/api/v1` response shapes frozen; `/api/v2` ships only after internal normalization is stable

- **Status:** Accepted
- **Date:** 2026-04-21

## Context

`/api/v1` is the public surface today. External platforms consume it —
TradingView alerts, GoCharting, Chartink, Amibroker, Excel, Python SDKs,
AI agents via the MCP server. The response shapes are baked into
user-written code we cannot coordinate with.

The refactor introduces new domain types, new persistence, and new
translators. It would be tempting to express the new shape as the v1
response shape and call it "cleaned up" — but any byte-level change to
a `/api/v1` response body will break user scripts silently.

We also need a place to *expose* the new domain vocabulary publicly.
`NormalizedOrderRequest`, `InstrumentRef`, `NormalizedQuote` — these do
not fit in v1's Indian-shaped responses.

## Decision

`/api/v1` response shapes and field names are **frozen** for the entire
duration of this refactor (Phase 0 through Phase 9).

- No field renames, no reordering, no type changes, no added fields, no
  removed fields, and no change in JSON key order where a client might
  rely on it.
- Internal callers are permitted — in fact required — to shape v1
  responses by translating *from* normalized domain types *back into*
  the legacy shape at the edge.
- A Phase 0 parity harness
  (`tests/parity/run_parity.py`) captures golden
  fixtures of every migrated service's output and runs every subsequent
  phase against them.

`/api/v2` arrives in **Phase 6** and not earlier. v2 endpoints:

- Return the normalized domain DTOs directly.
- Are additive — v2 appearing does not retire v1.
- Have their own OpenAPI schema and their own contract tests.
- Are **not** generated by copy-pasting v1 handlers. They wrap the same
  service functions but emit normalized shapes.

## Consequences

**Positive**

- Users do not experience a silent break during the refactor. The
  acceptance criterion is trivially checkable: `tests/parity/` must pass
  at every phase boundary.
- v2 design is not constrained by v1 backward-compat compromises.
- The refactor becomes easier to review: "does this PR change a v1
  fixture?" is a one-line question.

**Negative**

- For the lifetime of the refactor, every new concept exists twice —
  once in normalized form internally, once as a legacy-shape adapter at
  the v1 boundary.
- Once v2 ships, some users will want to migrate and some will not. We
  will carry both indefinitely unless a future ADR retires v1.
